# 面向用户的清晰报告

把报告写成用户可以独立阅读、理解和据此行动的成稿。普通报告直接写清楚；用户明确要求通俗化报告时，先保存专业稿，再据此重写通俗稿。专业稿供核对与接续，通俗稿供用户阅读；两者的事实和判断保持一致。

## 触发与默认模式

在报告、调研、可行性评估、复盘、审计、方案说明、交付说明等场景使用。先判断本次属于哪种模式：

- **普通报告**：一份完整、清楚、面向用户的成稿，不强制另建专业稿。
- **通俗化报告**：用户提到“通俗”“讲人话/说人话”“讲大白话”“白话”“更亲和”“更好懂”“少术语”等，且本次要产出或改写报告时，执行下面的双层流程。无需再等用户明确要求“两份”。
- **短文本解释或一句话进度**：直接改写并核对原意，不为此创建两份文件，也不套完整报告结构。

通俗化模式先读 [通俗化写作指南与范例](references/plain-language-guide.md)。指南包含用户认可的范例所体现的表达方法、改写示例和信息保真要求；不要求访问原用户设备上的文件。

## 通俗化报告：先有专业稿，再换讲法

1. **确定事实版本**。阅读原材料，先识别当前结论、历史结论和后来更新。多份材料有冲突时核对来源，不能把旧建议与新结论拼成一个故事。来源未核实的内容保留其状态；重写不自动升级证据。
2. **保存专业稿**。用 Markdown 保存完整、可独立理解的专业版本：问题与背景、对象与术语、证据与来源、关键数据及口径、分析结论、限制、方案与下一步。只记录可分享的事实、依据和必要推导，不记录模型私有思维过程。已有专业稿完整且适用于本次任务时直接复用，不复制一份充数；若只是局部摘录或缺少新结论，先补齐或另存更新版，保护原稿。
3. **从读者的问题重新组织**。写通俗稿时先解释“这在解决什么问题、为什么值得关心”，再讲怎么运作、数字说明什么、有哪些选择、接下来怎么做。不是逐句替换术语，也不是缩写摘要。使用指南中的问题标题、具体动作、受约束的类比和信息分层；根据本次内容选择，避免机械复刻页数或配色。
4. **对照检查信息保真**。逐项核对关键结论与理由、数字与样本口径、比较条件、方案与取舍、反向结果与限制、工作量与下一步、来源及验证状态。每项在通俗稿正文或其附录中均应找得到；不能把“详情请读专业稿”当作删除必要信息的理由。仅用户明确要求缩写、限定范围时才按该范围删减。
5. **按阅读用途交付**。专业稿与通俗稿默认使用同一中文主题名，并用“专业稿”“通俗版”区分，遵循全局或用户指定的报告目录规则；先落盘专业稿，再生成通俗稿。默认重点展示通俗稿，专业稿可在通俗稿的资料说明中链接，不要求用户依次读两遍。用户要求两个版本时再并列呈现。

专业稿不是只存在于上下文中的草稿。通俗稿发现专业稿算错、矛盾或缺项时，先核实并修订事实依据；不要为了双版一致而保留错误，也不要让两版静默分叉。

## 先站在读者一侧

- 默认读者有计算机基础，但没有参与当前项目的具体实现。不要假设读者知道历史对话、内部缩写、目录结构、实验编号或团队约定。
- 开头先回答四件事：这份文档在判断什么、现在得到什么结论、对项目有什么影响、接下来最应该做什么。短报告可把四件事合并成一段。
- 正文按“结果 → 含义 → 关键依据 → 风险/限制 → 下一步”推进。不是每篇都必须使用这些标题，但信息顺序要清楚。
- 每段只承担一个主要意思。使用完整的中文主语、动词和因果关系；不要把多个结论、缩写、指标、状态和内部名称压成一个长句。
- 用自然的中文解释“为什么这件事重要”。不要用名词堆叠、直译英文句式、过度被动句或看似正式但读不通的短语代替解释。
- 术语第一次出现时，给出一句短解释，并说明它为什么影响当前结论。后续可以使用简称；如果术语不影响读者判断，就不要放进正文。
- 不要为了显得严谨而反复声明同一条边界。把真正影响决策的限制集中到“限制与风险”部分，其余来源、路径和过程细节放到附录或可展开内容。

## 技术内容如何保留

- 保留会改变判断的数字、时间、对象、状态、证据、依赖、限制和因果关系；同时说明数字的统计口径，不让读者猜分母或状态含义。
- 明确区分“已经完成”“观察到的结果”“基于结果的解释”“建议下一步”和“尚未验证的假设”。不要把候选、试验、内部回放或结构通过写成正式结论。
- 只把必要证据放在正文。原始路径、命令、哈希、内部运行编号、完整指标表和复现步骤放进表格、附录、脚注或可展开细节；当它们直接影响判断、复现或用户明确要求时再展开。
- 对多个限制做归并：先说明它们共同影响的结论，再列最关键的两到四项。不要在每个章节结尾重复一遍“不能证明什么”。
- 用户只问项目完成情况、可行性、影响或下一步时，优先回答这些问题，不主动倾倒实现过程、方法名称、文件路径和工具调用记录。

## 报告结构建议

按任务需要选用，不要机械套模板：

1. **结论摘要**：用普通中文说清当前判断和最重要的原因。
2. **已经完成与结果**：说明做了什么、覆盖到哪里、哪些结果可以确认。
3. **这意味着什么**：把结果翻译成对项目、用户或决策的实际影响。
4. **关键依据**：保留足以支撑判断的数字、对照、来源和验证状态，并解释口径。
5. **限制与风险**：只列会改变结论、影响使用或阻止下一步的事项。
6. **下一步**：按优先级给出可执行动作，说明完成条件或停止条件。
7. **附录/细节**：放术语表、原始指标、路径、命令、完整来源和复现资料。

## 交付前核对

写完后核对以下事项：

1. 一个不了解前文的读者，能否仅凭开头知道这份文档的结论和影响？
2. 关键数字、状态、限制和下一步是否保留，且没有改变原意？
3. 每个必须保留的术语是否已经解释；删掉它是否会影响判断？
4. 正文是否把用户真正需要的信息放在前面，是否把内部过程和证据材料放到了合适的细节层？
5. 通俗化模式下，专业稿是否已实际保存或确认可复用？通俗稿是否覆盖其实质信息，且没有把推测写成事实、把局部观察写成普遍结论？

让语言变容易，同时保持事实、风险和判断的强度。普通报告直接交付清楚的成稿；通俗化报告保留专业稿，重点呈现用户能看懂、能判断、能继续行动的版本。

普通进度更新或一句话状态回答不触发完整报告结构；但只要用户要求形成报告、复盘、评估或交付说明，就按本 Skill 的读者视角组织内容。

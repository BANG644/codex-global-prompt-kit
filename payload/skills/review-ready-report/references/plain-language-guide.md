# 通俗化报告：易懂且完整的表达指南

仅在用户要求通俗化报告时读取。本指南配合主 Skill 的“专业稿 → 通俗稿 → 信息保真核对”流程，帮助在不牺牲准确性和信息量的前提下，让读者更容易理解。

本文中的项目、人物和数字均为通用或虚构示例，不对应任何真实项目、研究数据或用户文件。

## 1. 先让读者知道自己在看什么

开篇先回答：这件事想解决什么、当前最值得关注的结论是什么、它会影响什么决定。

- 读者没有参与过项目时，先补足理解结论所必需的背景，解释系统或流程中的角色各自做什么，再给结果表。
- 复杂报告可以提供两种阅读路径：先快速了解主要判断，再继续阅读完整依据、选项、风险与行动。摘要是入口，不能替代完整正文。
- 不要把“请先阅读前一版”作为理解前提。首次出现的版本名、实验组和内部代号，都附上功能性解释。
- 不强制套用固定卡片数、章节数或页面数；结构应服务于读者理解。

## 2. 用具体动作解释术语，而不是给术语换个别名

先说明对象在做什么，再给必要术语。原术语有助于查资料或复现时保留；纯内部名称可放附录。首次解释后使用同一叫法，避免同一对象在各节反复换名。

| 专业表述 | 可复用的解释方式 |
|---|---|
| 阶段 A / 阶段 B | 第一个环节定位问题出现的位置；第二个环节结合证据判断问题类型。保留 A/B 标签，方便读者对照图表。 |
| 交接材料 / handoff | 交给下一环节的内容，究竟只有结论，还是还包含依据、处理记录和可见回复。 |
| 2×2 因子设计 | 分别改变两个条件，将它们组合成四种情况后比较结果。 |
| 端到端通过 | 一项结果必须满足预先说明的全部关键条件，才算整体通过。 |
| 多标签判断 | 允许一个对象同时对应多个类别，并分别说明判断依据，而不是强行只选一个。 |
| 消融实验 | 每次只改变一个条件，观察结果是否随之变化，以判断它可能起了什么作用。 |

## 3. 按读者会追问的问题组织段落

可按任务需要选择以下顺序，不要机械套用：

1. **这到底在解决什么问题？** 先有真实场景和困扰。
2. **现有方案怎么运作，卡在哪里？** 用角色、材料流转或操作步骤说明。
3. **我们怎么比较，发现了什么？** 先解释条件与指标，再给数据。
4. **为什么会这样，对我们有什么用？** 区分观察、可能解释和建议。
5. **有哪些方案，各自要付出什么？** 比较收益、已有基础、成本与风险。
6. **先做哪件事，做到什么程度？** 让行动与理由相连。

章节标题写实际内容。例如“把处理记录一起交给下一步，为什么可能有帮助”，通常比只有“架构效用分析”更容易理解。正文围绕“发生了什么 → 为什么影响结果 → 我们该怎么做”展开，不必把这三个词印成固定标签。

## 4. 类比可以帮助理解，但不能替代机制

- 先尝试用具体例子直接解释；抽象关系仍难理解时，再引入贴近任务的类比。
- 用一两句说明类比中的角色如何对应真实系统，随后回到实际机制。类比只能帮助理解关系，不能充当证据。
- 不强制全篇比喻，不在每段重复“用大白话说”。避免把读者当儿童，或为了亲和加入戏剧性判断。
- 只描述实际可见的输入、回复、检索和工具记录；不要声称能读取模型未公开的内部思考。
- 如果类比把系统角色比作人，明确说明实际执行者是什么，避免让读者误以为做过真人评价。

## 5. 数字后面要有含义，含义必须受数字约束

**以下数字和场景均为虚构的表达示例，不代表任何真实项目或研究。**假设两种方案使用同一基准进行比较：方案 A 的完成率提高 8 个百分点，方案 B 提高 13 个百分点，两种提升相差 5 个百分点；每种条件覆盖 20 个案例，每个条件重复 3 次，共 4 个条件。

**合适的通俗改写：**

> 在只交接结论的方案 A 中，提供参考答案后，完成率提高了 8 个百分点；在还交接处理记录的方案 B 中，提高了 13 个百分点。两种方案的提升相差 5 个百分点。这提示交接材料可能影响后续环节使用参考答案的效果。不过，每种条件只覆盖 20 个案例，还需要更多数据检查这种差异是否稳定。

清楚的改写保留了比较对象、各自变化、差值、可能解释和样本限制；没有让读者猜“提高了多少”指哪个环节，也没有把局部结果夸大成整个系统效果。

- 每个关键数字至少说明对象、条件、单位和比较基准。百分比与百分点不能混用。
- 区分独立样本数与总运行次数：上面的 20 个案例 × 3 次重复 × 4 个条件 = 240 次运行，不能写成 240 个不同案例。
- 表格先解释“每行在测什么、每列改变什么”，再指出值得看的差异，不让用户独自解码。
- 有多项指标时，不用一个“正确率”概括所有指标；单环节变好不自动代表整条流程同幅度变好。
- 使用统一精度；摘要允许约数，但正文保留可核对的精确值，避免同一数字无说明地变化。

## 6. 限制同样要说成人话

**示例：**两个方案来自不同批次的测试，只能作为旁证。

> 另一组测试使用了不同条件，不能直接和这里的方案 A、方案 B 比高低。它可以帮助提出解释；要判断哪个方案更好，还需要按同一套条件重测。

**示例：**在某项条件下，方案 B 的指标比方案 A 低了 2 个百分点。

> 没有参考答案时，增加处理记录的方案在这次比较中反而低了 2 个百分点。因此目前不能把“多传过程记录”当作一定有效的改进；需要继续检查结果是否稳定，以及新增材料是否带来干扰。

这些数字也是虚构示例。真实报告中，限制应跟着它影响的判断出现，说明这会怎样影响选择；复现细节再放附录。不必在每段后面列一串抽象的“证据边界、依赖边界、适用边界”。

## 7. 信息分层，而非删掉信息

| 放置位置 | 内容 | 目的 |
|---|---|---|
| 开篇导读 | 问题、主要结论、影响、推荐动作 | 快速建立整体理解 |
| 正文 | 背景、机制、比较、关键数字、方案、风险、下一步 | 不依赖专业稿即可作判断 |
| 通俗稿附录或展开区 | 详细指标、完整对照、来源、术语、必要命令与复现信息 | 保留信息量，并支持进一步核查 |
| 专业稿 | 完整事实与技术分析及资料索引 | 支持其他 AI 或专业人员接续、复核 |

正文可以调整叙述顺序、合并重复论述，但不能静默丢弃专业稿中的反向结果、未选方案及其理由、成本、关键来源或未完成事项。逐项核对可在专业稿末尾记一张简短对照表，注明信息位于通俗稿哪一节；不为此另造一套日志文件。

用户只要指定范围的短版时，按其范围压缩并明确该版本是摘要，不宣称“全部信息保留”。

## 8. HTML 怎样帮助阅读

- 长篇内容可用导读、主题导航、卡片、对照表或图解；按内容选形式，不固定页面数或卡片数量。
- 标题、图注、单位和图例本身要讲得明白。卡片不是装饰：每张说明一个问题、一项发现或一种选择，避免把正文切成零碎口号。
- 关键限制靠近对应结论；详细来源和复现材料可以展开查看。词典是补充，不能替代首次出现时的解释。
- 保证正文可选择、复制，布局可适应手机；导航支持键盘，并保留打印及脚本失效时阅读全部内容的方式。交互不应把必需信息藏到无法访问的页面。
- Markdown 同样采用这些内容原则，无需为了通俗化强制改成 HTML。涉及 HTML 时结合 `html-delivery` 处理文件与布局。

## 9. 范例中值得修正的写法

学习易读的表达方式，不照搬过强判断：

- “这种做法是有害的”改成“在这次条件下，该指标出现下降”，并说明是否还要检查稳定性。
- “结果永远唯一”改成“在这批样本中，结果均为唯一”，不跨出实际样本范围。
- “能通过审核”“没有人做过”“可以推广到任何领域”不能只因表达亲和就写成事实；应分别说明现有优势、检索范围和待验证的推广设想。
- “所有案例都正确”若只覆盖被选中的一部分，就要说明范围，不能当成全部样本的准确率。
- 类比保持因果方向。例如下游能看到记录，不能写成“因此决定了上游能否用好答案”。
- 不把整体统计指标说成每一个具体案例的保证；说明数字的计算口径和适用范围。

## 完成条件

读者只看通俗稿，就能说明“研究或工作在解决什么、现在发现什么、为什么这么判断、还有什么拿不准、下一步怎么选”；专业读者能追溯关键数字、条件和来源。两版事实一致，通俗稿的主张强度没有上升，重要信息可在正文或附录找到。
